\section{探测复杂度与球槽分配模型}

开放寻址哈希表可被抽象为在线状态下的球槽分配问题\cite{aamand2021dynamic,bansal2022deletions}，假设表里有固定的槽位数，每个槽位最多只能存储一个元素；系统具有动态插入和删除的功能，任何时候元素的数量都不能超过槽位的数量，对于任意键 \(x\) ，哈希计算会生成一条预先确定的随机探测序列。

\[ h_1(x), h_2(x), \cdots ,\]
元素只会被安排到此序列指定的诸多候选槽位之中。

当某元素最终被置于其探测序列的第\(i\)个候选位置时，探测复杂度\footnote{查询时需记录“元素落在第 \(i\) 个候选位置”所需的比特数，记为 \(\Theta(1+\log i)\)，与辅助元数据空间直接相关。}被定义为 \(\Theta(1+\log i)\)。这一数量可被视为查询期间记录“元素采用第几个候选位置”所需的比特数目，因此与辅助元数据的空间开销存在直接关联。在该模型中有两个指标需同时把控：其一为平均探测复杂度，其对应的是整体附加空间；其二是交换成本，其指的是一次更新过程中被搬移元素的数量。最优哈希表理论所探讨的核心要点，是在允许有限交换的条件下，尽力减小平均探测复杂度。

\section{k-kick 树分层驱逐思想}

k-kick 树并非一种实际的树形数据结构，而是一种规则，此规则将固定长度的数组依照下标抽象成树的形式，第一层包含 \( s_0 = n \) 个元素，第二层则包含两个子区间，每个子区间有 \( s_1 = \frac{n}{2} \) 个元素，以此类推，下一层的两个元素由上一层均分而来，若已知元素位于某层的区间范围，便能推断出它上层所属的区间，由此生成的树形结构便是 k-kick 树的核心理念，但它本质上仍然是数组，这种结构会把一个 cubby 中按顺序排列的槽位分配到 \( k + 1 \) 个逻辑层级之上，而且各层级的大小随层级加深而依次变小，深层的 cubby 更靠近元素的随机偏好位置，因而具有较高的放置优先级；而表层的 cubby 覆盖范围广，主要用于收纳很多无法存放在深层位置的元素。

在进行插入操作之前，哈希过程会为元素明确一条从深层到浅层的Cubby路径，并且会给出该元素可使用的最大深度。插入时系统会尝试深层的Cubby；若目标Cubby处于已满状态但仍可调整，则可将其中优先级较低的元素踢出，随后将当前元素放置于该位置，被踢出的元素会再向更浅层寻找合法位置。因为每一次踢出均按照层级方向推进，所以级联进程会受到层数的限制。

参数\(k\)控制着层数，所以单次更新过程里的迁移次数能被限制在大约\(O(k)\)这个数量级，论文\cite{bender2022otsh}表明，在这种交换成本情况下，平均探测复杂度可缩减到大概\(O(\log^{(k)}n)\)，文章后面会记载kick\_count，而且会在实验说明里把理论 k-kick 树和当下工程版踢出链区分开来。

\section{紧凑元数据存储核心思想}

分层放置虽然会使探测变得不那么复杂，但在执行查询时，仍需知道元素最终处于哪个Cubby及其所对应的槽位，理论框架里用到了MiniArray和Local Query Router这两个部件，MiniArray用于解决变长元数据的存储问题，Local Query Router则负责处理局部键与槽位之间的映射关系。

MiniArray用以存储处于同个Cubby之中但长度存在差异的元数据条目，该理论方案借助内存 B 树及查表法来执行变长比特串的打包过程，可以做到在均摊常量时间里完成读写动作，其空间代价与条目的总计比特数成正比关系，不必给每个槽位都按最大条目长度分配空间。打包式哈希表\cite{kurpicz2023pachash}与紧凑检索结构\cite{pagh2008retrieval}在工程上提供了相近的“按条目实际长度计费”思路，但更新模型与本文的动态踢出路径并不相同。

Local Query Router主要承担对小规模键集合进行本地定位的职责。其将键映射为随机比特串，借助二进制前缀树区分不同的键，之后把树结构以及叶子上的槽位信息编码成连续的比特流。由于每一个Router仅负责管理局部的少量元素，因此前缀树的预期规模相对较小，能够在较低的空间开销情况下实现键到Cubby以及Slot的映射。第三章中的Router与MiniArray均依照该接口语义来实现，但其更新途径采用了简化处理方式。

\section{分层架构整体设计思想}

本文工作用Facility - Cubby - Slot这种三级架构来组织数据，Facility承担表格区域划分和路由任务，Cubby负责本地存储及元数据守护，Slot对应格子中的实际数组位置。

Cubby是局部存储单元，其内部存有存储槽，可变长度的元数据以及空闲槽检索构造，承担元素的放置，局部的驱逐以及键恢复所涉信息的维护任务。Facility对多个Cubby进行聚合，并且借助局部Router将键精准定位到目标Cubby以及相应的槽位。理论架构当中还引入了多 tiered Cubby\footnote{按层级 \(j\) 组织不同容量与数量的 Cubby 集合，配合 tail 与拆分/合并维持高装填因子与均摊扩容。}以及 tail\footnote{各 Facility 唯一允许未满载的 Cubby；新插入默认进入 tail，删除非 tail 元素时由 tail 回填以维持其余 Cubby 接近满载。}机制，非 tail Cubby尽可能维持处于满载状态，因插入与删除所引发的局部性波动主要由 tail 承受。

为了能够实现动态扩容和缩容，论文提出了多 tiered Cubby 机制，取一个 1-tiered cubby 作为 tail cubby，每次插入元素都插入 tail cubby 中，为了维护不变量，保持 j-tiered cubby\footnote{tiered Cubby 及不同层级的 j-tiered cubby 在第三章详细说明，此处从略。} 的装满状态以便实现均摊低成本的扩容和缩容以及逼近 1 的装填因子。当删除的元素不在 tail cubby 中时，会从 tail cubby 取出一个元素放入对应 cubby\footnote{该回填通过插入操作完成，用于维护对应 cubby 的 k-kick 树优先级与各层饱和状态。}。同时，不同 j-tiered cubby 的数量以及大小需要维护：设 \(t_j\) 为 j-tiered cubby 的理想数量，若真实数量远低于 \(t_j\)，则尝试将一个 \((j+1)\)-tiered cubby 拆成 \(t_j\) 个 j-tiered cubby；若 j-tiered cubby 过多，则合并为一个 \((j+1)\)-tiered cubby。具体细节在第三章阐述。

\section{商压缩的信息论最优思想}

正常情况下，哈希表若于槽位中完整保留原始键，则部分信息会与寻址过程重复。商压缩借助可逆双射映射 \(\pi\)\cite{bender2022otsh,pagh2008retrieval}，取映射后的低位作为路由；路由既知后，槽位只需保存剩余高位与少量恢复信息，从而达到空间压缩的效果。

具体而言，\(\pi(x)\) 的低 \(\log N\)位用来确定 Facility，Router 桶和局部偏好位置；槽位只保存去除该部分之后的 payload，若要复原完整的  \(\pi(x)\)，元数据记载偏好槽位与实际槽位的差值，还有局部桶里的中间位，再加上 Facility 编号，槽位下标和 payload，系统就能重新创建置换值，然后经由 \(\pi^{-1}\) 得到原本的键，第三章会遵照当下代码里的 payload、mid\_bits 和 delta 来阐述这个过程。

\section{算法层次全景总结}
上述的理论结构可概括为三方面：
\begin{itemize}
   \item Facility 负责组织 Cubby、维护 tail、承载扩缩容和重建过程中的局部管理。
   \item Router 负责把键映射到目标 Cubby 与 Slot，并为查询提供局部定位信息；
   \item Cubby 负责元素放置、空闲槽检索、局部 k-kick 树和变长元数据编码；
\end{itemize}
后续的章节会把这三方面当作系统开发的结构参考，并且阐述理论结构和实际达成之间的差别：第二章说明理论机制，第三章对应到代码实现，第四章再依据实际测试结果解释当前实现的行为边界。
