\chapter{系统验证与实验设计}
\label{ch:exp}

\section{实验目标}

本章针对第三章达成的核心路径展开验证，考察功能的正确性，操作时延，累计指标及结构快照，实验不是用来替代第二章的概率分析，也无法证明空间的最优点，它的评价标准仅仅包含三个问题：第一，插入，查询，删除以及重复插入是否符合接口语义；第二，Router，MiniArray，商压缩和工程版 k-kick 当下这种完成形式存在多少时延成本；第三，移动次数，路由步数以及元数据位数等记录数值能不能体现主要的运行状况。

\section{功能正确性测试}
otsh\_tests 是系统自动化回归的入口点，其包含以下测试步骤：

\begin{itemize}
 \item 初始化哈希表之后，要核查其返回状态以及表状态里的  \(N\)和 Facility 数量是否合法。
 \item 固定随机种子以生成唯一键集合，并开展批量插入操作，需保证每一个新键均满足 inserted=true。
 \item 对已插入的所有键开展查询，需得到 found=true；的结果。
\item 随机删除一半键，要求删除操作成功；
\item 再次查询已删除键，要求返回未命中；
 \item 对剩余键执行重复插入操作，并且要求其返回  inserted=false，以此来验证幂等语义。
\end{itemize}

测试结束时输出单行 JSON，字段包括 all\_passed、通过和失败数量、各测试用例名称与结果，以及 ops\_insert、ops\_query、ops\_delete、insert\_moved\_total、delete\_moved\_total 等摘要指标。该输出用于判断回归是否通过，并为后续性能实验提供基本状态参照。

\section{性能基准}

otsh\_perf 用来度量内存态哈希表路径，此程序未与 MySQL 相关联，也未经由 HTTP JSON 进行编解码，目的在于减小存储层及接口层对于插入，查询，删除所历时延的不良影响，该程序具备命令行参数 n\_insert，n\_rand\_queries 和 table\_n\_hint，而且依靠环境变量 OTSH\_SEED 来固定随机种子。

每个阶段记录操作数、吞吐、平均延迟与 p50 分位数。文本结果输出到 stderr，单行 JSON 输出到 stdout，便于脚本收集到 perf/results/。本文实验参数为 n\_insert ${}=5\times10^4$、n\_rand\_queries${}=2\times10^5$、table\_n\_hint ${}=2\times10^5$、OTSH\_SEED${}=1$。

程序运行完毕之后，会输出哈希表的状态以及累计指标，相关结果见表~\ref{tab:otsh-perf-metrics}，此阶段系统包含 25000 个元素，其中 active 表规模为 65536，\( K = 256 \)，Facility 数量为 256，插入移动次数总计为 46941，单次移动次数最多为 5；删除移动次数总计为 376，单次移动次数最多为 1。这个结果表明，在工程版 k - kick 插入时确实存在槽位搬移现象，但在当前参数设置下，单次移动次数未超过 5，Router 访问步数的最大值为 5，这显示在固定随机种子和当前规模的情况下，局部 Patricia 路由并未产生过深的访问路径，要注意的是，meta\_bits\_total 和平均上报元数据位数是逻辑统计量，不能直接折算成进程实际所占内存大小。
